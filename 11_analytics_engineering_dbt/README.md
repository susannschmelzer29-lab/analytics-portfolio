# 11 · Analytics Engineering — Service Delivery Warehouse (dbt + DuckDB)

A dimensional model for a **social-services provider**: what was delivered,
by whom, under which funding stream, and whether the teams were staffed
for it. Built with dbt on DuckDB, layered staging → intermediate → marts,
with 61 tests that run in CI.

**Stack:** dbt-core 1.12 · DuckDB · Python · GitHub Actions

```bash
pip install -r requirements.txt
python scripts/generate_seeds.py          # deterministic synthetic source data
cd dbt && DBT_PROFILES_DIR=$PWD dbt build # 11 models, 61 tests
```

Runs offline. No warehouse account, no credentials, no network.

> ## ⚠️ Honesty note — read this first
>
> **The data is synthetic and generated by a script in this repository.**
>
> Real service-delivery records from a social-services provider are special
> category personal data under Art. 9 GDPR. They cannot go into a public
> portfolio, and anonymising a small district-level dataset is not safe
> enough to change that.
>
> What this means for the figures:
>
> * The **structure** — grain, keys, funding logic, capacity maths — mirrors
>   how such an organisation is actually run.
> * The **levels** do not. A 0.33 utilisation rate is an artefact of random
>   assignment in the generator, not a claim about any real provider.
> * The generator plants **five deliberate defects** so the tests prove
>   something. See [`docs/data_quality.md`](docs/data_quality.md).
>
> The point is to demonstrate modelling method and data-quality reasoning,
> not to publish numbers about anyone.

## The question this model answers

> *We deliver X hours of support across five cost centres funded from four
> different sources. Are we staffed for what we actually deliver, and how
> much of the work has no funder behind it?*

That second half is the one that matters in this sector. Documentation,
case conferences and travel are real work with no billing code. The
`unbillable_share` column in `mart_funding_mix` is the figure that ends up
in a budget negotiation.

| Funding source | Hours/year | Unbillable | Share |
|---|---:|---:|---:|
| Integration Assistance | 7,696 | 1,521 | 19.8 % |
| Donations | 2,651 | 515 | 19.4 % |
| Municipal Funding | 2,558 | 519 | 20.3 % |
| Youth Welfare | 2,530 | 428 | 16.9 % |

*(synthetic figures — see the honesty note)*

## The three decisions worth explaining

### 1. Severity is split by who owns the problem

This is the decision I would defend in an interview.

| Test finds… | Severity | Why |
|---|---|---|
| A broken reference, an impossible date, a negative duration | **warn** | The source system is wrong. I do not own it. My job is to report it, loudly and every run — not to fail a build I cannot fix. |
| A duplicated grain, a reconciliation gap, utilisation above 2.0 | **error** | *My* model is wrong. The build must stop. |

Without that split you get one of two failure modes: a permanently red
pipeline that everyone learns to ignore, or source defects quietly
swallowed to keep it green. Both end with nobody looking.

`store_failures: true` on the warn tests writes the offending rows into a
table, so "1 warning" is followed by "here are the rows".

### 2. Bad rows survive into the fact table

`int_services_enriched` uses **left** joins, not inner joins. An orphan
`staff_id` therefore reaches `fct_service_delivery` and trips the
relationship test.

An inner join would have been tidier and would have hidden exactly the
defect worth finding. The marts exclude those rows from aggregates with an
explicit `where`, so the numbers stay right — but the row is never
silently gone.

The one exception is exact duplicates, removed in `stg_services`: a row
delivered twice by the transport layer is not a fact about the world.

### 3. Assumptions live in one place

Capacity maths needs two numbers that are pure judgement: 4.33 weeks per
month and a 12 % absence allowance. Both sit at the top of
`int_staff_capacity_monthly` with a comment saying they are assumptions —
not buried in a dashboard formula where nobody can argue with them.

The reporting window and the full-time week live in `dbt_project.yml`
under `vars`, so changing the period touches no model at all.

## Layers

```
seeds/         raw_*          generated CSVs, treated as the source system
  ↓
staging/       stg_*          views · rename, cast, one model per source
  ↓                           no joins, no aggregation, no business rules
intermediate/  int_*          ephemeral · the joins and the capacity maths
  ↓
marts/         dim_ / fct_ /  tables · what a dashboard queries
               mart_
```

| Model | Grain |
|---|---|
| `fct_service_delivery` | one delivered service event |
| `dim_client` · `dim_staff` · `dim_service_type` | one entity |
| `mart_utilisation_monthly` | cost centre × month |
| `mart_funding_mix` | funding source × quarter |

Stating the grain is not decoration: every additive measure in
`fct_service_delivery` is only correct while it holds, and the uniqueness
test on `service_id` is what keeps it holding.

## Tests

61 total: 57 pass, 4 warn — one warning per planted defect that reaches the
fact table.

**Generic** (in `_staging.yml`, `_marts.yml`): uniqueness and not-null on
every key, `relationships` on every foreign key, `accepted_values` on care
level and funding source.

**Singular** (in `tests/`), the ones that need real domain logic:

| Test | Catches |
|---|---|
| `assert_no_service_before_client_entry` | work recorded before admission |
| `assert_no_service_after_client_exit` | work recorded after discharge |
| `assert_duration_is_positive` | sign errors, aborted entries |
| `assert_utilisation_within_sane_bounds` | arithmetic gone wrong, not overtime |
| `assert_revenue_matches_fact_table` | a mart inventing or losing money |

The reconciliation test is the most valuable of the five. A wrong join or
a dropped filter changes a total; no column-level test would notice.

## A bug this project found in itself

The first version of the generator assigned services to clients without
checking whether the client was in care that day. Result:
`assert_no_service_before_client_entry` fired **1,496 times**.

That is not a finding, it is noise — a test that always screams is a test
nobody reads. The generator was fixed to draw only from clients active on
the given date, and the count dropped to exactly 1: the defect that was
planted on purpose.

Worth recording, because it is the normal case: the first thing a data
test catches is usually a mistake in your own pipeline.

## Limitations

* No snapshots. Client care levels change over time; this model treats the
  current value as the only value. A slowly-changing dimension would be the
  next step and is a real gap, not an oversight.
* Capacity is contracted hours, not rostered hours. A real provider would
  model shifts.
* No incremental models. At 11k rows a full rebuild takes under a second;
  incrementality here would be complexity without benefit.
* Utilisation levels are generator artefacts. Only the method transfers.
